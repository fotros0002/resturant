## 6. قوانین معماری

### 6.1. Multi-tenancy

هر مشتری تجاری یک Tenant مستقل است.

تمامی رکوردهای عملیاتی باید به Tenant معتبر وابسته باشند. اطلاعات شعبه نیز باید با BranchContext معتبر کنترل شود.

Tenant ID دریافت‌شده از مرورگر نباید منبع قابل اعتماد تشخیص هویت مستأجر باشد.

تمام Queryها، سرویس‌ها و APIهای مربوط به اطلاعات مشتری باید محدود به Tenant مجاز باشند.

### 6.2. Authorization

مجوزها به‌صورت Server-side کنترل شوند.

مجوز استفاده از هر قابلیت باید حاصل ترکیب این موارد باشد:

- اشتراک فعال
- ماژول مجاز
- نقش کاربر
- مجوز عملیات
- محدوده مجموعه یا شعبه

### 6.3. Licensing

پیاده‌سازی موتور لایسنس باید امکان موارد زیر را فراهم کند:

- Trial
- Active
- Grace Period
- Suspended
- Expired
- Cancelled

قوانین دقیق دوره مهلت، پرداخت ناموفق و دسترسی پس از انقضا باید در سند سیاست اشتراک تعریف شوند.

با انقضای لایسنس، عملیات غیرمجاز متوقف شود؛ اما اطلاعات حذف نشوند.

حق مشاهده یا استخراج داده باید مطابق سیاست قرارداد و الزامات قانونی حفظ شود.

### 6.4. Financial Integrity

- پول با نوع داده دقیق ذخیره شود.
- تغییر قیمت محصول روی فاکتورهای قبلی اثر نگذارد.
- تمام تراکنش‌ها قابل حسابرسی باشند.
- جلوگیری از ثبت سفارش و پرداخت تکراری الزامی است.
- تراکنش‌های مالی باید Atomic باشند.
- ابطال و استرداد با ثبت اسناد اصلاحی انجام شود.
- گزارش فروش با اطلاعات تسویه و صندوق قابل تطبیق باشد.

### 6.5. Extensibility

هسته نباید به پیاده‌سازی یک ماژول خاص وابسته شود.

هر ماژول باید دارای موارد زیر باشد:

- شناسه و نسخه
- وابستگی‌های مشخص
- مجوزهای دسترسی
- تنظیمات
- Migration
- API
- منوها و صفحات
- آزمون‌های اختصاصی
- سیاست فعال‌سازی و غیرفعال‌سازی

## 10. تست‌های اجباری

حداقل سناریوهای زیر باید تست شوند:

1. مشتری A نتواند اطلاعات مشتری B را مشاهده کند.
2. شعبه A نتواند اطلاعات شعبه B را بدون مجوز مشاهده یا تغییر دهد.
3. کاربر بدون مجوز نتواند تخفیف خاص اعمال کند.
4. ماژول غیرفعال از طریق API نیز غیرقابل استفاده باشد.
5. لایسنس منقضی نتواند عملیات ممنوع را انجام دهد.
6. تمدید اشتراک، داده‌ها و مجوزها را به‌درستی حفظ کند.
7. چند درخواست هم‌زمان، سفارش تکراری نسازند.
8. پرداخت تکراری به‌اشتباه ثبت نشود.
9. فاکتور فروش بعد از تغییر قیمت منو تغییر نکند.
10. ابطال فاکتور، سابقه اصلی را حذف نکند.
11. موجودی انبار در عملیات هم‌زمان منفی یا ناسازگار نشود؛ مگر طبق سیاست مجاز.
12. فاکتور فارسی به‌درستی چاپ شود.
13. نمایشگر آشپزخانه آیتم‌های ایستگاه خود را نمایش دهد.
14. تسویه نقدی و کارتی به‌صورت ترکیبی درست عمل کند.
15. صندوق پایان شیفت و مغایرت را درست محاسبه کند.
16. نسخه موبایل برای گارسون قابل استفاده باشد.
17. از نسخه پشتیبان، داده‌ها واقعاً بازیابی شوند.
18. Migration بدون تخریب اطلاعات قبلی اجرا شود.
19. قطع ارتباط باعث اعلام موفقیت کاذب عملیات نشود.
20. محصول بدون CDN و درخواست‌های خارجی غیرمجاز اجرا شود.

برای هر سناریو، وضعیت PASS، FAIL یا NOT RUN همراه با شواهد واقعی ثبت کن.

## 11. معیارهای پذیرش

هیچ ماژولی صرفاً با داشتن صفحه ظاهری تکمیل‌شده محسوب نمی‌شود.

هر ماژول برای پذیرش باید:

- فرآیند عملیاتی کامل داشته باشد.
- به پایگاه داده واقعی متصل باشد.
- اعتبارسنجی Backend داشته باشد.
- مجوزهای صحیح را اجرا کند.
- خطاها را درست مدیریت کند.
- آزمون‌های مربوط را پاس کند.
- روی موبایل و دسکتاپ بررسی شود.
- مستندات و شواهد داشته باشد.

استفاده از داده نمایشی فقط در محیط Demo و Test مجاز است.

8. وضعیت دقیق پذیرش
9. شماره Commit و لینک PR در صورت دسترسی به Repository
10. بسته ZIP سورس و مستندات مرحله

تمام فایل‌ها و گزارش‌ها در قالب ZIP بسته‌بندی شده و در صورت دسترسی به سرویس Picofile در آن بارگذاری شوند و لینک‌ها ارائه گردند. اگر بارگذاری ممکن نبود، بسته‌های ZIP قابل دریافت تحویل داده شوند؛ لینک جعلی ارائه نشود.

## 13. اصول کار با Git

- Repository موجود را ابتدا بررسی کن.
- اگر Repository مشخص نیست، از ایجاد Commit در پروژه نامرتبط خودداری کن.
- برای هر Gate یک Branch مستقل ایجاد کن.
- تغییرات را در Commitهای مشخص ثبت کن.
- بدون تست و تأیید لازم به شاخه اصلی Merge نکن.
- فایل‌های حاوی اطلاعات حساس، رمزها و داده واقعی مشتریان نباید Commit شوند.
